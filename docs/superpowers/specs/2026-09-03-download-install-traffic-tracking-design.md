# DJL Download, Install, and Traffic Tracking Design

## Goal

Extend PR #15 so DJL can measure three distinct production signals:

1. landing-site page views and anonymous unique browsers;
2. installer download clicks routed to GitHub Releases or Alibaba OSS; and
3. unique desktop installations after the downloaded application first launches.

The feature must preserve PR #15's explicit worldwide and China download buttons, must never delay
or block a download or application launch, and must not collect IP addresses, names, email
addresses, usernames, project data, or application-usage data.

## Definitions and limits

- A **page view** is one client-side landing route view that reaches the same-origin visit endpoint.
- A **unique visitor** is one browser profile holding DJL's anonymous first-party visitor cookie.
  It is an estimate, not a person count: clearing cookies or using another browser creates a new ID.
- A **download** is one successful landing redirect decision. It is a click/redirect count, not proof
  that the complete installer bytes arrived. Direct links that bypass the landing site are not
  recorded in D1.
- An **install** is one random installation ID reported from a packaged desktop build. It is
  de-duplicated by D1 and is a better approximation of installed copies than download counts.
- GitHub's native asset `download_count` and Alibaba OSS access logs remain independent origin-side
  signals. This feature does not replace them or claim that any request count equals a human count.

## Current state

PR #15 (`codex/landing-oss-downloads`) contains the explicit GitHub and China download controls and
resolves China selections to immutable objects in the Hong Kong OSS bucket. It does not report
downloads.

A previous local branch, `backup/local-main-before-landing-cleanup-20260903`, contains tested but
unmerged implementations for:

- a deployed `djl-stats` Worker and D1 database;
- landing download reports split by `github` and `oss`;
- a one-time packaged-desktop install ping; and
- release-build injection of `DJL_STATS_URL`.

The live Worker exists at `https://djl-stats.slcor.workers.dev`, has D1 binding `DB`, and has the
`STATS_READ_TOKEN` secret. The live D1 database currently contains the `downloads` and `installs`
tables and no rows. The canonical repository, the PR branch, and the separate landing deployment
repository do not yet contain the earlier tracking implementation. There is no page-visit schema or
endpoint.

## Architecture

The existing `djl-stats` Worker remains the single analytics backend. PR #15 will add or restore
four independently testable pieces:

1. Worker ingestion and protected summaries for visits, downloads, and installs.
2. A same-origin landing visit endpoint and a tiny route-aware client reporter.
3. Download reporting in the existing redirect routes after the redirect response is committed.
4. A one-time desktop install ping whose URL is embedded by the signed release build.

No dashboard UI is added to the public landing site. Owners read the protected JSON summary or run
read-only D1 queries.

## D1 schema

The already-applied `0001_init.sql` migration remains immutable. A new `0002_visits.sql` migration
adds:

```sql
CREATE TABLE visits (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts TEXT NOT NULL,
  visitor_id TEXT NOT NULL,
  path TEXT NOT NULL,
  country TEXT
);
CREATE INDEX visits_ts ON visits (ts);
CREATE INDEX visits_visitor_id ON visits (visitor_id);
```

`visitor_id` is a random UUID generated by the landing server. It is not derived from an IP
address, user agent, or other fingerprint. A page view inserts one row. Unique visitors are computed
with `count(DISTINCT visitor_id)`.

## Worker API

### `POST /v1/visits`

Accepts:

```json
{
  "visitorId": "uuid",
  "path": "/guide",
  "country": "CA"
}
```

Validation requires a UUID, an absolute site path beginning with `/`, no query or fragment, a
maximum length of 256 characters, and an optional two-letter uppercase country. A valid request
inserts one page view and returns 204.

### `POST /v1/downloads`

Accepts `{ platform, arch, source, country?, version? }`. `source` is exactly `github` or `oss`.
The endpoint inserts one redirect event and returns 204.

### `POST /v1/installs`

Accepts `{ installId, version, platform, arch, channel? }`. It uses `INSERT OR IGNORE` keyed by
`installId`, making retries idempotent. Cloudflare supplies the request country because this request
comes directly from the desktop application.

### `GET /v1/stats`

Requires `Authorization: Bearer <STATS_READ_TOKEN>` and returns:

```json
{
  "visits": {
    "pageViews": 0,
    "uniqueVisitors": 0,
    "byCountry": {},
    "byPath": {},
    "byDay": []
  },
  "downloads": {
    "total": 0,
    "bySource": {},
    "byCountry": {},
    "byPlatform": {},
    "byDay": []
  },
  "installs": {
    "total": 0,
    "byCountry": {},
    "byPlatform": {},
    "byVersion": {},
    "byDay": []
  }
}
```

Daily arrays cover the latest 30 UTC days and fill missing days with zero. Ingest bodies remain
limited to 4 KiB. Invalid bodies return 400, wrong methods return 405, unknown paths return 404,
and all responses use `cache-control: no-store`, a restrictive CSP, and `nosniff`.

## Landing visit flow

`VisitReporter` is a client component mounted once in the root layout. It watches `usePathname()`
and sends `POST /api/visits` once after each pathname change. It sends only `{ path }` and ignores
network failures.

The same-origin `/api/visits` route:

1. validates the path;
2. reads an HttpOnly first-party cookie named `djl_visitor_id`;
3. creates a cryptographically random UUID when the cookie is absent or invalid;
4. reads the two-letter country from Vercel's `x-vercel-ip-country` header;
5. schedules the Worker report with Next.js `after()`; and
6. returns 204, setting the cookie when it created one.

The cookie uses `HttpOnly`, `Secure` in production, `SameSite=Lax`, `Path=/`, and a 180-day maximum
age. The reporter does not send query parameters or hashes, preventing accidental capture of
tokens or user-entered URL data.

## Landing download flow

The Windows and architecture-specific macOS redirect routes keep PR #15's existing
`resolveDesktopDownload(target, request)` decision. The decision result is extended to include both
the destination and a report containing platform, architecture, selected source, visitor country,
and resolved release version.

Each route schedules `POST /v1/downloads` with `after()` and immediately returns the existing 307.
Worker failures, timeouts, and rejected events are swallowed so analytics can never break the
download. The architecture-agnostic macOS route remains a release-page redirect and is not counted
as an installer download.

## Desktop install flow

Packaged desktop builds create `<userData>/install-record.json` containing a random UUID and report
state. On startup:

1. development builds and builds without a validated stats URL do nothing;
2. a missing or invalid record is replaced with a new UUID record before any request is sent;
3. an unreported record posts app version, platform, architecture, and update channel to
   `/v1/installs`;
4. a successful response stamps `reportedAt`;
5. a failure leaves the record pending for the next launch; and
6. the operation never blocks or rejects Electron startup.

`desktop-release.yml` passes repository variable `DJL_STATS_URL` to the artifact build. The build
validates a credential-free HTTPS URL and writes it to `extraMetadata.djlStatsUrl`, which the
packaged application reads. The public README discloses the one-time anonymous message.

## Privacy and abuse boundaries

- No IP address is stored. Vercel and Cloudflare may process network metadata as infrastructure
  providers, but DJL stores only their two-letter country result.
- No user agent, referrer, query string, hostname, account identity, device name, or application
  content is collected.
- The anonymous visitor cookie is first-party and HttpOnly; it is not a cross-site advertising ID.
- Public ingest endpoints cannot safely contain a shared secret. Strict validation, body limits,
  de-duplication of install IDs, and owner-side comparison with GitHub/OSS origin metrics are the
  intended integrity controls.
- The protected read endpoint compares bearer tokens without an early-exit string comparison.

## Failure behavior

Analytics fails open. A Worker or D1 outage must not prevent a page from rendering, a redirect from
being returned, or the desktop app from starting. Visit and download reporters use short timeouts
and discard failures. Install failures retry on the next launch with the same persisted ID.

Deployment is ordered to avoid client/server skew:

1. deploy the backward-compatible Worker code;
2. apply D1 migration `0002_visits.sql` before traffic can reach `/v1/visits`;
3. push PR #15 so its checks run;
4. mirror/deploy the landing site;
5. merge PR #15 only after required checks are green; and
6. ship a later desktop release only through the repository's guarded release command.

No release tag or PR merge is part of this task unless the user requests it separately.

## Testing and verification

- Worker unit tests cover visit validation, routing, inserts, protected summary queries, zero-filled
  days, and existing download/install behavior.
- Landing unit tests cover visitor cookie creation/reuse, path validation, country normalization,
  route-change reporting, GitHub reports, OSS reports, redirect fail-open behavior, and unchanged
  redirect destinations.
- Desktop tests cover install record parsing, UUID creation, URL validation, payloads, successful
  stamping, retries, and startup failure isolation.
- Build-script tests cover safe `DJL_STATS_URL` metadata injection.
- Typecheck, lint, formatting, focused tests, the landing production build, Worker dry-run build,
  and the repository's public-source audit run before the PR is updated.
- Live verification confirms the Worker binding and secret, applies migrations, deploys the Worker,
  exercises synthetic events with recognizable IDs/paths, reads the resulting rows, and removes
  only those exact synthetic rows afterward so production totals remain clean.
- PR #15's title/body are updated to describe the additional analytics feature and report the fresh
  verification evidence. The branch is pushed; the PR is not merged automatically.
