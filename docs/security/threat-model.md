# DJL Security Threat Model

## Overview

DJL is a local-first agent workspace comprising an Electron desktop shell, a Node.js WebSocket server, a React web renderer, provider subprocesses such as `codex app-server`, an iOS remote-control application, a local remote gateway, and a metadata-only Cloudflare relay. It can read and modify repositories, execute approved tools and terminal commands, manage Git state, and transmit task context to the user's selected AI provider. These capabilities make host credentials, source code, task transcripts, approval decisions, long-term device identities, and software-update integrity the primary assets.

This review covers the whole repository, with deeper focus on the new remote path in `apps/ios`, `apps/remote-gateway`, `apps/remote-relay`, `packages/remote-protocol`, and its Electron integration. It is based on repository revision `fab119f80f1114f859c3834e43ebf7c53d512fa1` plus the hardening and documentation changes on the same feature branch.

Security objectives:

- only the local user, an explicitly paired phone, or a locally authorized DJL client can control agent tasks;
- task content remains confidential and tamper-evident across the remote relay;
- provider, terminal, Git, and filesystem actions remain within the user-visible approval and access policy;
- device and session credentials are not exposed through logs, renderer IPC, QR payloads, pushes, or release metadata;
- update and release artifacts cannot silently redirect clients to an attacker-controlled relay;
- resource exhaustion, reconnects, partial streams, and crashes fail predictably without replaying actions.

## Threat Model, Trust Boundaries, and Assumptions

### Assets and security-sensitive operations

- Repository contents, uncommitted changes, Git credentials, SSH keys, environment variables, local databases, Codex rollout history, and terminal output.
- Prompts, responses, reasoning summaries, attachments, images, voice input, approvals, tool results, and task-routing metadata.
- Desktop owner-session tokens, WebSocket authentication material, provider credentials inherited by child processes, and update-signing credentials.
- The computer Ed25519 private identity, relay host/notification secrets, phone Ed25519 private identity, trusted-device registries, APNs signing key, device tokens, and relay administrator token.
- High-impact actions: shell execution, patch application, file writes/deletes, Git commit/push/PR operations, browser/tool access, provider approvals, device replacement, session revocation, and software updates.

### Trust boundaries

1. **Desktop renderer ↔ Electron main/preload.** Renderer content is less trusted than the privileged main process. Context isolation and a narrow preload API must prevent arbitrary Node/Electron access. Remote IPC exposes only sanitized status, QR data, enable/reset controls, and update requests.
2. **Browser/web app ↔ local Node server.** HTTP and WebSocket requests cross an authentication, origin, and loopback boundary. Owner-session tokens, trusted-origin checks, CORS rules, and path validation are required even when the service normally binds locally.
3. **DJL server/gateway ↔ provider subprocesses.** Codex and other provider runtimes execute with the desktop user's operating-system authority and receive selected task context. JSON-RPC inputs and outputs are untrusted structured data.
4. **Agent/tool request ↔ host filesystem, terminal, and Git.** Tool parameters can target sensitive paths or destructive operations. The user approval mode and path/worktree constraints are the authorization boundary.
5. **iPhone ↔ untrusted network ↔ Cloudflare relay ↔ computer.** Cloudflare and the network are trusted for availability and routing only, not confidentiality or command authenticity. Application frames require endpoint-to-endpoint authentication and encryption.
6. **QR display/camera ↔ device trust.** The person scanning a visible, unexpired QR receives an opportunity to authenticate as the new phone. Device-owner authentication and short expiry reduce accidental or remote capture; physical observers remain relevant.
7. **Relay ↔ APNs.** Apple receives generic notification content and routing metadata. APNs credentials authorize notification delivery but must not authorize DJL task control.
8. **CI/release pipeline ↔ installed clients.** GitHub Actions, package registries, signing services, release variables, Electron update metadata, Apple signing, and Cloudflare deployment control shipped code and endpoints.

### Trusted components and assumptions

- The user's operating system, Secure Enclave/Keychain implementation, installed DJL binary, signed iOS binary, and authenticated provider CLI are not already compromised.
- The computer and iPhone have cryptographically secure random-number generators and correct enough clocks for short expiry windows.
- Ed25519, X25519, HKDF-SHA256, SHA-256, and AES-256-GCM remain secure and are used through platform/runtime cryptographic implementations.
- A user who approves a provider/tool action understands that the selected provider and tool receive the shown data and host authority.
- Cloudflare and APNs may inspect their normal network/routing metadata, deny service, delay messages, or lose state; they must not be able to forge endpoint identities or decrypt task content.
- Public open-source dependencies, GitHub Actions, and upstream model/provider binaries are supply-chain dependencies, not intrinsically trusted content.

### Attacker capabilities

In scope:

- an unauthenticated remote Internet attacker who can connect to public relay endpoints and send malformed or high-rate traffic;
- a malicious or compromised relay operator who can observe metadata, reorder/drop/replace opaque frames, and return malicious registry data;
- a nearby observer who photographs a QR before it expires;
- a malicious web page attempting localhost requests, WebSocket connections, or renderer compromise;
- a compromised provider response or repository content attempting prompt injection, path traversal, terminal injection, unsafe links, or resource exhaustion;
- an attacker with a stolen but locked iPhone, or with access to iOS backups;
- a dependency, CI credential, release variable, update feed, or signing-key compromise;
- a normal local user accidentally driving the same persisted task from desktop and phone concurrently.

Out of scope, but still operationally important:

- an attacker who already has arbitrary code execution as the same desktop OS user can read repositories, control processes, and may read the gateway's user-only fallback state file;
- a fully compromised iOS kernel, unlocked device with the owner's passcode, malicious accessibility stack, or compromised Secure Enclave;
- the selected AI provider retaining or misusing data according to its own service terms;
- traffic analysis that derives coarse activity patterns only from timing and encrypted sizes.

### Security invariants for future changes

- No plaintext task content, previews, filenames, terminal output, or model text may enter relay storage, logs, analytics, or APNs payloads.
- Long-term private keys and per-session secrets never enter a QR, renderer IPC response, registry record, crash report, or release metadata.
- Identity changes always require explicit re-pairing; registry data alone never updates a pinned identity.
- Pairing, reconnect, and encrypted-frame schemas remain versioned and validated on both platforms.
- Remote capability additions reuse the existing encrypted request channel and the same local authorization policy; they do not add public relay APIs for privileged actions.
- Destructive operations remain explicit and recoverable where possible. Remote access does not broaden the OS authority of the local DJL process.

## Severity Calibration

DJL uses four practical security severities:

- **Critical:** unauthenticated remote command execution; task-control impersonation; private key, provider credential, or signing-key disclosure; update compromise; cross-workspace arbitrary file write/delete without approval. Block release, disable the affected route/update channel, rotate or revoke credentials, and require re-pairing when identity integrity is uncertain.
- **High:** plaintext task/repository disclosure; approval bypass; replay of mutating actions; persistent unauthorized phone access; renderer-to-main privilege escalation; broadly exploitable resource exhaustion. Fix before public release or immediately revoke/disable the affected feature.
- **Medium:** metadata leakage beyond the documented boundary; limited denial of service; confusing concurrent ownership; recovery behavior that can duplicate a non-destructive action; security control disabled only through an already-authorized local setting. Schedule promptly and add regression coverage.
- **Low:** bounded information exposure with no task content, defense-in-depth gap, or hardening/documentation issue requiring another weakness to exploit. Track and fix during normal maintenance.

Severity is raised when exploitation is remote, unauthenticated, cross-workspace, persistent, invisible to the user, or affects release/signing infrastructure. It is lowered only when a prerequisite already grants equivalent authority—for example, arbitrary code execution as the same desktop OS user. Availability attacks by the relay remain at least Medium because remote control is a core feature; compromise of endpoint authenticity or task confidentiality is never treated as an availability-only issue.
