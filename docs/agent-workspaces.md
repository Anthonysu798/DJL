# Agent workspaces

Workspaces replaces the Kanban navigation entry. The `/workspaces` routes show a terminal canvas; old `/kanban` links still open the replacement. Existing chat/task records are preserved.

## Use it

1. Open **Workspaces → New workspace**. Choose a saved project or click the folder icon beside Working folder. Electron opens the native directory picker on macOS or Windows; manual paths remain available. Picking a folder fills an empty workspace name and matches an existing project without overwriting a custom name.
2. Choose **Add account**, select the provider, optionally add a label, and click **Sign in with [provider]**. DJL immediately launches that profile's official CLI login in a dedicated dialog; no workspace pane is created. A known provider authorization URL enables **Open sign-in page** as a browser fallback.
3. Complete the provider's sign-in. DJL checks the profile's CLI-reported identity and enables **Use this account** when it is signed in. Closing the dialog stops only its sign-in terminal; the CLI owns the credentials. Cancelling a startup waits for it before closing, preventing an orphaned login process. A cancelled account remains available for retry from its **Sign in** action.
4. Click a signed-in account in the sidebar to select it for new terminals. **New terminal** remembers that selection; opening terminals also remembers the chosen account. Existing panes keep their original profile. The edit icon renames a profile or removes an unused profile from the list; removing a profile is not a provider logout.
5. Use Split/Grid, maximize/restore, or the pane's plus button. Closing a pane stops only its process. Closing a workspace stops all its panes after confirmation. Switching workspaces keeps their processes running. Agent `/exit`, interruption, failed startup, or an updater exit returns to the same interactive shell and working folder; no Restart button is required.

A plain Shell terminal can run any installed CLI. OpenCode profiles can authenticate the model providers supported by OpenCode, including coding-plan providers. Native Codex, Claude, and Cursor CLIs must be installed and discoverable by DJL; explicit provider binary paths are honored. For automatic Codex selection, each launch compares installed versions across PATH and the standard Bun/npm global directories, so an updated Bun copy is not hidden behind an older npm copy. Inherited package-manager launch metadata is removed to avoid misdirecting the CLI updater.

## Account isolation

Profile metadata, workspace organization, and terminal identities persist locally in renderer storage. Credentials never enter this store. They remain under CLI control in `DJL_HOME/userdata/terminal-accounts/<provider>/<opaque-profile-id>` (or the CLI's profile-scoped OS credential store).

- Codex: separate `CODEX_HOME` per account, explicit file credential storage, and separate `CODEX_SQLITE_HOME` per terminal. The latter avoids concurrent first-launch database migration races while retaining shared account authentication.
- Claude Code: separate `CLAUDE_CONFIG_DIR` per account.
- Cursor: separate `CURSOR_CONFIG_DIR` per account.
- OpenCode: separate XDG config/data/cache/state directories per account.

Provider API keys, OAuth overrides, and host-agent identity variables are removed from the inherited launch environment. The server computes directories and argv from a validated profile id; renderer environment overrides cannot change the selected account. Signing into one profile never copies credentials from an existing personal installation or another DJL profile.

The Accounts & subscriptions list shows the login status reported by each profile’s CLI: green for signed in, red for signed out/unavailable/unconfirmed, and a neutral dot during the initial check. It preserves the chosen profile label and displays the reported email underneath. Codex uses its profile-scoped app-server `account/read`; Claude uses `auth status`; Cursor uses `status`; OpenCode uses its provider credential listing. API-key identities and CLIs that do not expose an email show “Email unavailable.” Emails and raw status output are not written into the persisted workspace store, and tokens never enter the renderer response. Checks are cached for 30 seconds, refreshed every minute while visible and on window focus, and can be refreshed with the account-list refresh button. Terminal counts do not determine authentication status.

These are account selectors, not pooled subscriptions or a quota bypass. Real account identity, paid entitlement, token refresh, and provider limits are determined by the provider. A generic shell does not claim managed account isolation for unknown CLIs. The profile labels are user-chosen names, not verified billing identities.

## Resource usage

Workspace processes are independent of their visible terminal renderers. Panes initialize shortly before entering the viewport and keep their parser and input surface while the workspace stays active. Offscreen painting pauses, and hidden output is batched without animation-frame wakeups. Scrolling back needs no terminal-open request or screen replay. Visited workspace canvases stay mounted and switch visibility, retaining their recorded viewport visibility without repeated geometry reads. Leaving Workspaces for another page parks initialized renderers while their PTYs continue running. Returning reattaches the same xterm instances before paint, without terminal-open requests or snapshot replay. Scrollback, selection, unfinished input, workspace scroll position, maximized pane, and last terminal focus survive workspace and page navigation. Focus restores on workspace return, not on unrelated updates. Only explicit terminal/workspace closure disposes retained renderers; a full app quit still ends this renderer lifetime.

Interactive PTYs advertise `COLORTERM=truecolor` and their supported `TERM`. Launcher-only `NO_COLOR`, `FORCE_COLOR`, and `CLICOLOR` overrides are removed so provider CLIs render their own native colors. Explicit per-terminal environment overrides remain supported. Existing CLI processes retain the environment they started with; this change applies to new sessions after the backend is updated.

Workspace panes use the DOM renderer, avoiding WebGL texture-atlas corruption during repeated resizing. They also disable image decoding, ligature shaping, and cursor blinking. Startup is queued with two concurrent launches; attaching an existing profile skips CLI discovery and account-file preparation. Each independently running agent CLI still consumes its own CPU and memory.

The 24-terminal browser fixture checks output acknowledgements, retained input surfaces, zero reopen requests on return scrolling, and zero WebGL allocations. A separate 6 + 13 terminal fixture switches workspaces 30 times, checks stable terminal/DOM/subscription counts and view state, and records click-to-paint p95 plus available heap measurements. These timings use a mocked PTY backend. Reconnect tests verify one snapshot request per retained renderer after an actual transport interruption, no process restart for exited panes, and cleanup when a parked terminal is explicitly closed. Split/grid tests check Unicode text and renderer continuity through repeated maximize/restore cycles. Retaining viewed panes uses more memory than immediately destroying them, but avoids the previous scroll-time reconstruction and misleading Connecting indicators. Buffers remain bounded by the terminal scrollback limit.

Keyboard input has an interactive echo path: the next small PTY chunk after a write bypasses the server batch timer, and the workspace renderer submits it directly to xterm without another frame queue. Subsequent bulk output remains batched. Workspace keys skip orchestration-thread title lookups. `terminalLatency.test.ts` compares managed and direct PTY echo on Unix; `terminalInputLatency.browser.tsx` measures keyboard-to-parser handling with a mocked echo transport. These measure separate stages, not total input-to-display latency.

## Verification

On 2026-09-05, the 6 + 13 terminal browser fixture measured 42 ms p95 for 30 warm switches with a mocked PTY backend and stable instance/subscription counts and reported heap size. A separate full-width Electron dev run with the real backend measured 64 ms p95 and 47 ms median over 30 warmed switches, with zero Connecting headers. All 19 real PTY shell process IDs matched before and after switching. Timing measures click dispatch through the second animation frame; it excludes initial CLI/MCP startup and does not measure provider response latency. Settings → chat → Workspaces was also visibly verified with retained screens. Earlier cold/profile runs included xterm task-queue warnings; these are not included in the warm-switch measurements.

Focused tests cover account directory isolation, ten sessions sharing credentials, per-terminal Codex databases, unsafe profile ids, terminal lifecycle, two groups of ten terminal assignments, workspace independence, localization, and reconnect handling. Computer Use QA exercises actual shell input, native CLI startup, batch creation, workspace navigation, and pane controls against the Electron dev app. The performance follow-up verified a 20-terminal saved session, background output across workspace switches, and restoring offscreen panes. Completing real provider authentication requires the account owner's sign-in; startup or a profile label alone does not verify a paid subscription.
